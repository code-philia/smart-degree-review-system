# 479 篇归档论文批量规则检测设计

## 目标

在“30条规则检测”的“历史报告”右侧增加“扫描479篇归档论文”。学院管理员和学校管理员可选规则 18、22、24、28 的任意非空组合，启动一次扫描当前归档目录全部 PDF 的任务，并持久查看每次任务、每篇论文、每条规则的结果及原文位置。部署后不自动启动扫描。

## 已确认的约束

- 归档根目录 `/opt/sjtu-archive-479` 当前恰好包含 479 份 PDF，总计 6.7 GB；21 份大于现有 50 MB 上传限制。以任务开始时枚举到的实际 PDF 数量为准。
- 两类管理员可发起任务并查看持久结果；学生和导师没有入口或 API 权限。用户已确认学院管理员与学校管理员均可查看全部 479 篇及所有检测结果；归档现有目录没有学院归属映射。
- 只调用现有本地四规则探测器，单篇 PDF 一次调用完成本任务选中的规则。保留“无法判定”和“扫描失败”状态，不把它们归为通过。规则 24 的提示需人工复核。
- 不复制或修改归档 PDF。报告保存相对路径、规则结果和 PDF 坐标；原文仅在打开详情时按需从归档目录读取。

## 工作流

第三页签显示四张规则卡，卡片上有单规则“扫描全部归档论文”按钮；复选框支持多选并统一启动。页面显示当前任务进度、已处理/总数、发现问题/无法判定/失败数，以及历次任务。单个任务结果可按规则、结论和论文名筛选并分页；点开论文可查看每条规则结论、问题说明、页码和高亮原 PDF。

## 后端

新增归档扫描 API、持久化任务和逐篇结果表。任务启动时快照 PDF 相对路径列表；同一时间只运行一个任务，其余启动请求返回冲突提示。后台逐篇执行，每篇失败后记录原因并继续。每篇完成立即写库；服务重启时将未完成项重新排队续跑。使用固定归档根目录配置；所有 PDF 请求仅使用服务端生成的结果 ID，验证真实路径仍位于根目录内，禁止客户端传入文件路径。所有 API 由两类管理员权限保护。PDF 响应支持 Range 请求，以适配大文件。

## 前端

第三页签属于 `/thirty-rules-check/archive` 路径，侧栏保持“30条规则检测”选中。任务详情及论文详情也在该前缀下。前端轮询运行中任务，已完成任务停止轮询。PDF 组件扩展为可接收同源 URL，沿用已有坐标高亮和问题联动。

## 验收

- 单规则和多规则任务都逐篇处理目录全部 PDF，任务历史可重开；失败或无法判定有独立状态。
- 未登录、学生、导师不能访问 API；两类管理员按最终确认的范围访问。
- 归档原文件不被复制或更改，支持超过 50 MB 的 PDF 和原文定位。
- 页面切换、刷新与服务重启后任务进度和结果不丢失；新路由保持侧栏选中。
- 运行前后端测试、lint、类型检查和构建；部署后核查公开路由、服务健康与发布版本。数据库备份仍按现有脚本默认跳过。
