# 修复建议功能：需求—设计—实现审查

> 审查对象：当前工作区代码、`handoff/开发交接说明.md` 与现有自动化测试。
>
> 审查范围仅限“已产生告警的修复建议”。本文不评价规则检测器本身，也不把未实现能力描述为已完成。
>
> 证据标记：**[已有依据]** 来自交接说明或现有界面/代码可直接证明；**[推断]** 是基于实现作出的产品解释；**[待确认]** 表示没有找到明确产品决定或有效验收证据。

## 1. 功能需求（WHAT & WHY）

### RS-01：为一条归档告警提供可执行的人工修复建议

- **目标及业务原因**：用户在查看归档论文的检测告警时，除看到“哪里可能有问题”外，还应获得如何处理的简明建议。交接说明要求输出具体建议并指向原文，而非自动修改论文。**[已有依据]**
- **输入**：一条已保存的归档告警、对应规则、告警定位/锚点，以及可从 PDF 获取的附近文本。
- **输出**：建议状态与一条或多条简明修改动作；每条动作附带其所依据的输入证据 ID。
- **用户可观察行为**：在归档论文详情中选中某条告警，可看到“AI 修复建议”；没有已有建议时可点击生成。
- **验收标准**：
  1. 用户可对一条具有有效定位的归档告警生成建议；
  2. 建议明确为人工参考，不改变原告警或 PDF；
  3. 返回内容至少有一个非空修改动作，且动作的证据引用来自本次输入。

### RS-02：建议必须受现有证据约束，不得把推测写成事实

- **目标及业务原因**：历史检测告警是候选问题而非已确认事实；若模型补造图、公式、数据或参考文献，会把风险从“待核查”扩大为错误引导。交接说明明确禁止虚构。**[已有依据]**
- **输入**：规则、告警、原始定位文字、已有锚点和 PDF 邻近文本。
- **输出**：基于这些信息的建议；证据不足时应指出还需核对/补取的内容；证据反驳告警时应标示冲突。
- **用户可观察行为**：建议底部显示“可执行建议”“需要补充上下文”或“证据与告警存在冲突”。
- **验收标准**：
  1. 模型请求明确禁止虚构，并限制证据 ID；
  2. 后端拒绝不存在的证据 ID、空动作和非法状态；
  3. 至少有针对“证据不足”和“证据冲突”的实例级或语义级验收。第 3 项目前未被有效验证。

### RS-03：同一告警在相同依据下可复用已生成建议

- **目标及业务原因**：避免用户每次打开页面都重复调用模型、产生额外成本和不稳定措辞；当规则、告警上下文或提示词发生变化时，旧建议不应被静默复用。**[已有依据：交接说明要求以上下文、模型和提示词版本区分缓存]**
- **输入**：告警关联标识、上下文内容哈希、模型/模型版本、提示词版本。
- **输出**：匹配时返回已保存建议；不匹配时生成并保存新建议。
- **用户可观察行为**：首次选中告警会读取已有建议；无建议时显示生成按钮。已有建议后，按钮文字为“重新获取建议”，但当前实现仍可能返回缓存，见第 4 节。
- **验收标准**：相同输入返回同一缓存记录；模型版本或提示词版本变化时不命中旧缓存。

### RS-04：建议生成过程不得破坏原扫描结果，并应可追溯

- **目标及业务原因**：建议是对原检测结果的附加解释，不能覆盖原始告警；发生争议时应能追溯使用的上下文、模型和提示词版本。**[已有依据]**
- **输入**：原归档扫描结果与新生成建议。
- **输出**：独立建议记录；记录来源、上下文版本、模型元数据和用量。
- **用户可观察行为**：用户看到原告警、原文定位和建议并存；建议显示模型及提示词版本。
- **验收标准**：保存建议后原扫描报告内容不变；建议记录可按告警查回，且有来源/版本元数据。

### RS-05：生成失败应可理解且不影响其他告警

- **目标及业务原因**：外部模型、PDF 文本提取和网络均可能失败；单条失败不应阻塞用户继续查看原结果或影响批量任务。**[已有依据：交接说明要求超时、格式错误和重试验证]**
- **输入**：模型超时、非成功响应、格式错误、无有效 PDF 页码或未提取到文本等失败情形。
- **输出**：明确错误响应；批量处理中保留该条失败并继续其余条目。
- **用户可观察行为**：告警卡显示“生成失败：……”；原告警和 PDF 仍可正常查看。
- **验收标准**：单条模型请求有限时；模型格式不合法或证据不存在时被拒绝；批量生成可在中断后继续处理成功项以外的记录。

### RS-06：为历史归档告警提供可审计的批量生成能力

- **目标及业务原因**：已有 1,023 条候选告警，逐条人工点击无法完成初步效果评估；需要在不改动原 PDF 和原扫描报告的前提下生成可复查样本。**[已有依据]**
- **输入**：历史归档结果导出、只读归档 PDF、模型配置。
- **输出**：独立数据库中的建议缓存，以及逐条记录请求、模型消息、响应/错误的审计文件。
- **用户可观察行为**：这不是正式网站功能；它为隔离预览提供已缓存建议。
- **验收标准**：批量运行可恢复；成功项不会重复调用；全部目标告警有成功响应或明确失败记录；原始 PDF 和原扫描导出不被修改。

## 3. 技术设计合理性审查

### 3.1 必要且合理的拆分

以下拆分直接服务于当前正确性或安全性，不是过度设计：

| 设计 | 审查结论 | 原因 |
| --- | --- | --- |
| 告警读取/请求构造与模型调用分离 | 必要 | 一个模块负责从可信归档数据定位告警，另一个模块负责不可信外部模型调用；边界清楚，也便于用模拟模型测试。 |
| PDF 上下文提取独立 | 必要 | Node 服务不直接承担 PDF 文本定位；路径校验和 Python/PyMuPDF 依赖隔离，且可以在模型调用前失败。 |
| 建议与扫描结果独立存储 | 必要 | 防止覆盖检测事实；同时支持缓存、版本追溯和多次建议。 |
| 上下文/模型/提示词参与缓存键 | 必要 | 只按告警 ID 缓存会在上下文或提示词变化后错误复用内容。 |
| 前端通用告警面板以可选回调接入建议 | 合理、轻量 | 避免复制一套告警 UI；普通检测页不传回调时仍保持原行为。 |
| 30 秒总超时 | 必要 | 外部模型响应体曾出现连接持续不返回的情形；仅取消 fetch 不能保证结束，显式拒绝可防止批任务卡死。 |

### 3.2 为后续扩展预留、但非当前归档功能必要的设计

| 设计 | 审查结论 |
| --- | --- |
| `repair-contract-v0.1.ts` 中的 `paper_ir` 来源、IR 节点字段和多种证据类型 | 面向未来 IR 接入的契约草案；当前运行代码只处理 `legacy_archive`。 |
| 数据库 `source_kind` 同时允许 `legacy_archive`、`paper_ir` | 未来兼容预留；并未实现 IR 适配。 |
| 批处理脚本的 `--concurrency`（上限 5） | 对长批任务的运行效率预留；实际批次以单并发完成，以避免 429 限流。 |
| `/request`、`/context` 两个调试接口 | 有助于核对模型真实输入，但不是用户生成建议的最小路径。其是否保留为正式 API 需要决定。 |

这些预留没有明显伤害当前实现，但应当在文档中明确“未实现的未来能力”，不能当作已支持功能。

### 3.3 可简化之处与结论

没有发现为了当前归档功能而必须立刻重构的重复业务逻辑。当前层次（适配 → 证据 → 缓存/存储 → 模型 → 路由 → 页面）与不同失败边界相对应，整体合理。

可选择的简化，不降低当前正确性：

1. 若调试接口不需要对外保留，可在未来仅保留内部测试/管理工具；这会减少两个公开路径，但会降低人工核对输入的便利性。
2. 批处理器可继续作为开发工具而非产品模块；不应因它存在而在正式网站增加不必要的批量管理界面。
3. `repair-contract-v0.1.ts` 与实际 `repair-response-v2` 字段不一致（草案含 `suggestion`、`rationale`、`missing_context` 等，当前实现只保留 `status` 和 `actions`）。应把草案明确标注为历史提案，或未来更新它；这是文档一致性问题，不是运行错误。

不能做的“过度简化”：把前端直接传来的文本交给模型、移除上下文哈希缓存键、把建议写回原扫描 JSON、或把 PDF 提取与模型调用混为一个不可测试步骤，都会降低安全性、可追溯性或正确性。

## 4. 需求缺口与不确定性

### 4.1 已明确且实现的需求

- 归档告警可生成、保存并展示独立 AI 修复建议；
- 建议不自动修改论文或检测结论；
- 模型输入受到规则、告警和局部证据约束；
- 同上下文、模型和提示词版本可复用缓存；
- 模型输出必须为受校验的结构化动作；
- 1,023 条历史归档告警已完成批量生成，保存于独立开发输出/数据库，不是生产数据。
- 单篇 PDF 检测的当前结果页和历史报告页已接入 AI 修复建议：仅三十六条支持规则显示入口，建议按报告所有者隔离保存，并可显式强制生成新版本。该增量的详细需求见《RS-07：单篇论文检测报告接入 AI 修复建议》。

### 4.2 需求明确但尚未实现或仅部分实现

| 项目 | 状态与依据 |
| --- | --- |
| 新 IR 告警接入 | 未实现。只有契约草案和数据库枚举预留。 |
| “关联对象”补证 | 部分实现。现有实现取告警摘录、锚点和同页邻近文本；没有按规则专门提取候选图表、公式目标、参考文献条目、目录正文标题或附录标题。交接说明对“关联对象”的要求比当前实现更宽。 |
| 重试限额 | 未实现。脚本可在下次运行时重试失败项，但没有最大次数或退避策略。 |
| 规则 13、14、29 的真实归档验收 | 无真实历史告警，不能由当前 1,023 条批量结果证明。 |

### 4.3 已有实现但原始需求未明确要求的内容

- `/request` 与 `/context` 调试接口；
- 保存完整提示词消息的批处理审计文件；
- 并发参数和本地批处理导入/种子逻辑；
- 页面展示模型名与提示词版本；
- 可选的通用告警面板回调接口。

这些功能有维护和审计价值，但是否应作为正式产品承诺，需要产品方决定。

### 4.4 三种建议状态的前端表现

| 状态 | 后端是否允许 | 前端当前表现 | 验收结论 |
| --- | --- | --- | --- |
| `suggested` | 是 | 显示动作，标注“可执行建议”。 | 有组件级渲染测试。 |
| `insufficient_context` | 是 | 仍显示动作，标注“需要补充上下文”。 | 代码可达，但没有组件或端到端测试，也没有真实样本验收。 |
| `evidence_conflict` | 是 | 仍显示动作，标注“证据与告警存在冲突”。 | 代码可达，但没有组件或端到端测试，也没有真实样本验收。 |

还需注意：后端不会根据“文本提取为空”自动返回 `insufficient_context`，而是返回 422 错误；三种状态由模型决定。因此“证据不足应显示为状态而非错误”的产品语义尚未完全确定。

### 4.5 修复建议质量的语义验收

当前具备的是**结构和运行验收**：JSON 可解析、状态合法、动作非空、证据 ID 存在、1,023 条可完成生成。

当前不具备可证明的**语义质量验收**：没有人工标注的金标准、抽样复核标准、规则维度评分表、虚构/误导率阈值，或针对每种状态的期望输出集。提示词约束和证据 ID 校验只能降低风险，不能证明建议正确、充分或真正可执行。

建议在进一步发布前由产品方确认至少以下验收口径：

1. 每条规则抽样多少份、由谁复核；
2. “可执行”“不虚构”“证据不足”分别如何判定；
3. `evidence_conflict` 是向用户直接展示，还是先作为内部人工复核信号；
4. 允许建议采用条件句的边界；
5. 多条建议、重复点击和“重新获取建议”是否应产生新版本。

## 5. 开发者理解指南：一条真实告警的完整数据流

贯穿案例：归档论文 `03300_020033910079_李子通.pdf` 中的规则 15 告警 `sjtu_rule_15_1`。该类告警表示某图未被全文引用；它是候选问题，不等于论文已经确定有错。

| 步骤 | 关键模块 | 输入 | 输出 | 目的 |
| --- | --- | --- | --- |
| 1. 用户打开详情 | `ArchiveScanResultPage` | 路由中的任务 ID、文档 ID | 已保存的论文扫描结果及告警列表 | 显示原始规则检测结论和 PDF 定位。 |
| 2. 用户选中告警 | `PaperLintWorkspace` → `FindingsPane` | 当前告警卡 | 当前活动告警键 | 联动 PDF 与右侧告警卡。 |
| 3. 页面读取已有建议 | `loadRepairSuggestion` → `GET /archive-findings` | 任务、文档、规则、告警四个标识 | 最近已保存的建议（若有） | 先复用结果，不产生模型调用。 |
| 4. 用户点击生成 | `generateRepairSuggestion` → `POST /archive-findings/evaluate` | 同一组四个标识 | 生成请求或缓存响应 | 由服务端决定是否需要模型调用。 |
| 5. 服务端定位可信告警 | `getArchiveFinding`、`buildArchiveRepairRequest` | 四个标识和归档扫描记录 | 规则原文、告警消息、定位摘录、锚点证据 | 防止客户端任意篡改模型依据。 |
| 6. 补取 PDF 邻近文本 | `resolveArchivePdfPath`、`extractPdfContext`、Python `extract` | 归档相对路径、目标页和定位框 | 同页附近最多 7 个文本块（最多 6,000 字符） | 给模型加入告警附近的原文，而非仅凭规则消息猜测。 |
| 7. 查缓存或请求模型 | `findRepairSuggestion`、`proposeRepair` | 完整请求、上下文哈希、模型和提示词版本 | 已有建议，或模型返回的结构化动作 | 避免重复调用；新请求最多等待 30 秒。 |
| 8. 校验并保存 | `validateModelAnswer`、`saveRepairSuggestion` | 模型 JSON | 独立建议记录 | 拒绝非法状态/证据 ID，不覆盖原扫描结果。 |
| 9. 页面展示 | `FindingsPane` | `status`、`actions`、版本元数据 | 建议文字及状态标签 | 用户据此人工核对并修订论文；系统不自动修改内容。 |

### 该案例的边界

当前第 6 步只保证取得告警附近的同页文本，不保证已经找到“图 2.3”或其全文引用的所有候选位置。因此模型给出的“补充引用”仍应理解为基于局部证据的人工修复建议，而非对全文的重新判定。

## 附：本次审查对现有说明的校正

`docs/repair-suggestions.md` 可继续作为功能概览；本文补充了它未区分的三类事实：

1. **功能完成**不等于**语义质量已验收**；
2. **三种状态已被协议和 UI 支持**不等于**三种状态均已有测试与真实样本验证**；
3. **局部 PDF 上下文已实现**不等于交接说明所说的全部“关联对象补证”均已实现。

## 2026-10-20 上线配置与约束

- 单篇当前结果、历史报告和归档结果提供修复建议；支持规则 11、13、14、15、16、18、22、24、28、29、31、32、33，以及共享目录中的23个基础检查项；其他规则隐藏入口并由 API 拒绝。
- 默认通过 `scripts/repair_model_proposal.py` 复用 `PAPER_COMPILER_CONFIG` 只读凭据及既有 `MaasClient`；不要求向网站进程另外复制原始 MAAS 密钥。Python 解释器优先使用 `REPAIR_MODEL_PYTHON`，其次 `SIX_RULE_PYTHON`。
- 所有真实请求复用 `/data/runtime/paper-compiler/budget.sqlite3`：累计上限沿用 500 元，与现有 website 阶段共享 20 元子额度。先预留后调用，单次输出最多 1024 tokens，最多尝试一次；失败或超时保留不确定占用，不重置历史费用。
- 查询已有建议不收费；缓存绑定当前规则、文档及告警身份和模型、提示词版本。用户要求生成新版本时使用独立生成标识，避免返回旧的模型缓存。
- 修复建议只供用户核对和人工修改，不改写 PDF、原始报告、检测结论或已完成归档任务。


### 规则 31—33 修复建议扩展（2026-10-20）

单篇当前结果、历史报告及归档结果均支持规则 31—33。引用规则请求保留告警中的原文、外部内容证据及规范摘要，并按模型输入上限汇总规范证据；规则/证据/程序版本变化会使缓存失效。31 仅建议修正已证实的格式问题；32 区分检索缺失与文献不存在；33 区分引用语境和文献内容，缺内容证据时不编造支持关系。费用仍由原有共享账本及 website 子额度控制。


## 默认显示修复建议（2026-10-20）

所有已上线检查项（13 个编号规则和 23 个基础检查项）在当前结果、历史报告、归档结果中自动读取已保存建议；没有有效建议时自动生成并保存。所有报警卡片直接展示建议，无须逐条选中或点击生成。保留“重新生成修复建议”，显式请求新版本，旧版本保留。证据不足和证据冲突会如实展示。

前端分开调度缓存读取（最多 3 并发）与生成（最多 2 并发），缓存不等待其他报警的慢生成。后端合并同一上下文的并发请求；失败不会在页面重绘时自动循环重试。权限和报告所有者隔离保持不变。

旧离线批量结果经原始请求、模型输入和 PDF 核对后迁入生产缓存，保留原生成时间、模型及原始上下文指纹，另外记录迁移来源和新的缓存绑定。网站运行时读取数据库。用户本轮授权 website 子额度为 20 元，累计总上限仍为 500 元，保留全部历史及不确定费用占用。
